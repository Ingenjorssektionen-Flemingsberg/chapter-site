## Overview

The chapter site serves as the central hub for engineering students at KTH Flemingsberg. It provides:

- Chapter news and announcements
- Calendar of events and gasques
- Information for newly admitted students (_Nyantagen_)
- Profiles and contact details for chapter organs, boards, and committees (_Organ och Nämnder_)
- Governing documents (_Styrdokument_), overall guides (_Ovve_), songbook, and student locker rentals
- Direct contact and student issue reporting (_JML_ / _Studienämnden_)

## Tech Stack

- **Runtime & Package Management:** [Bun](https://bun.sh/) / [Node.js](https://nodejs.org/) (npm)
- **Frontend Framework:** [React 19](https://react.dev/)
- **Language:** [TypeScript](https://www.typescriptlang.org/) (strict mode)
- **Bundler:** [Vite](https://vitejs.dev/) (via `rolldown-vite`)
- **UI & Component Library:** [Material-UI (MUI v7)](https://mui.com/) + `@emotion/react` & `@emotion/styled`
- **Routing:** [React Router v7](https://reactrouter.com/)
- **Icons:** Material UI Icons
- **Notifications & Forms:** [Notistack](https://notistack.com/) & [Zod](https://zod.dev/)
- **Authentication / OIDC:** `@react-keycloak/web` / `react-oidc-context`
- **Containerization & Web Server:** Docker (multi-stage build) + Alpine NGINX

## Getting Started

### Prerequisites

- **Bun** (recommended) `>= 1.1` OR **Node.js** `>= 20.x` with **npm**
- **Git**

### Installation

Clone the repository and install dependencies:

```bash
git clone https://github.com/isf-kth/chapter-site.git
cd chapter-site

# Using Bun:
bun install

# Or using npm:
npm install
```

### Development Server

Start Vite with hot module replacement (HMR):

```bash
# Using Bun:
bun run dev

# Or using npm:
npm run dev
```

The application will be accessible at `http://localhost:5173`.

### Production Build & Linting

```bash
# Type-check and build for production
npm run build

# Run ESLint checks
npm run lint

# Format code with Prettier
npm run format

# Preview production build locally
npm run preview
```

## Environment Configuration

### Available Variables

Create a `.env.local` or edit `.env.development` to customize your local environment:

| Variable              | Description                           | Default Example                                        |
| :-------------------- | :------------------------------------ | :----------------------------------------------------- |
| `VITE_API_URL`        | Base URL for the IsF backend API      | `https://isflemingsberg-backend.app.cloud.cbh.kth.se`  |
| `VITE_OIDC_URL`       | Keycloak / OIDC issuer authority URL  | `https://isflemingsberg-keycloak.app.cloud.cbh.kth.se` |
| `VITE_OIDC_CLIENT_ID` | OIDC client ID registered in Keycloak | `frontend`                                             |
| `VITE_OIDC_REALM`     | Keycloak realm name                   | `isflemingsberg`                                       |

### Runtime Injection via Docker & Nginx

Unlike traditional Vite applications where `import.meta.env` values are hardcoded at build time, this project uses dynamic runtime substitution:

1. During `docker build`, `scripts/docker-envs.ts` replaces environment variables with placeholder tokens (e.g. `__API_URL__`).
2. When the container starts up, `entrypoint.sh` (generated by `scripts/nginx-entrypoint.ts`) inspects the container's environment variables and replaces the tokens inside `/usr/share/nginx/html` before starting Nginx.
3. Therefore, when deploying the pre-built Docker image, you set standard environment variables (e.g. `API_URL`, `OIDC_URL`, etc., without the `VITE_` prefix) in your deployment manifest.

## Google Calendar Integration

The Events page (`/event`) displays calendar events pulled from the chapter's Google Calendar via the backend API service (`/api/calendar?from=...&to=...`).

### How It Works

1. The frontend queries the backend API (`src/services/calendar.ts`) for events within the active date range.
2. The backend communicates with Google Calendar using a Service Account or Google Calendar API Key.

### Creating a Google Calendar API Key & Calendar ID

If you are configuring or deploying the backend calendar provider:

1. **Open Google Cloud Console:**
   - Go to [Google Cloud Console](https://console.cloud.google.com/).
   - Create a project (e.g. `isf-calendar-service`).
2. **Enable Google Calendar API:**
   - Navigate to **APIs & Services** > **Library**.
   - Search for **Google Calendar API** and click **Enable**.
3. **Generate Credentials:**
   - Go to **APIs & Services** > **Credentials**.
   - Click **Create Credentials** > **API Key** (or create a Service Account if reading non-public calendars).
   - Restrict the API Key to only allow calls to the Google Calendar API and restrict HTTP referrers/IPs if applicable.
4. **Obtain Chapter Calendar ID:**
   - In Google Calendar web interface, open the settings for the chapter calendar under **Settings for my calendars**.
   - Ensure the access permissions are set to **Make available to public** (See all event details).
   - Scroll down to the **Integrate calendar** section and copy the **Calendar ID** (looks like `xyz...@group.calendar.google.com` or chapter email).
5. **Set in Backend:**
   - Add the calendar ID and credentials to the chapter backend deployment secrets.

## Deployment & kthcloud Pipeline

### Local Docker Build

Test building and running the production container locally:

```bash
# Build Docker image
docker build -t isf-chapter-site:latest .

# Run container on port 3000
docker run -p 3000:3000 \
  -e API_URL="https://isflemingsberg-backend.app.cloud.cbh.kth.se" \
  -e OIDC_URL="https://isflemingsberg-keycloak.app.cloud.cbh.kth.se" \
  -e OIDC_CLIENT_ID="frontend" \
  -e OIDC_REALM="isflemingsberg" \
  isf-chapter-site:latest
```

The app will be live at `http://localhost:3000`.

### GitHub Actions CI/CD to kthcloud

The repository includes automated CI/CD defined in `.github/workflows/cloud.yml`.

1. **Trigger:** Every push to the `main` branch or manual `workflow_dispatch`.
2. **Registry:** Builds and tags the Docker image, pushing to the KTH Cloud private registry:
   - Registry URL: `registry.cloud.cbh.kth.se`
   - Required repository secrets:
     - `DOCKER_USERNAME`: kthcloud registry robot/user account
     - `DOCKER_PASSWORD`: kthcloud registry access token/password
     - `DOCKER_TAG`: destination image tag (e.g. `registry.cloud.cbh.kth.se/isf/chapter-site:latest`)
3. **Deployment in kthcloud:** The kthcloud Kubernetes deployment pulls the updated image on release or webhook.

## Configuration & Site Settings (src/config)

Static site configurations and navigation hierarchies are managed centrally in `src/config/`:

### 1. `src/config/links.ts` (Link Registry)

Acts as the single source of truth for all URLs across the application to prevent broken links and hardcoded strings:

- **`LINKS.internal`**: Application routes (e.g., `/sektionen`, `/qm`, `/rudan`, `/styrdokument`).
- **`LINKS.social`**: Chapter and committee social links (Instagram, Facebook, LinkedIn, Linktree, TikTok, Discord server invite).
- **`LINKS.mail`**: Official chapter mailto links (styrelsen, ordförande, valberedningen, ovve purchases, etc.).
- **`LINKS.docs`**: Direct links to official chapter governance documents (bylaws/_stadgar_, economic reglementen, brand guidelines, and ovveguide PDF).
- **`LINKS.ths` & `LINKS.mit`**: External student union links (THS main site, membership portal, partner chapter MiT, and RKHSK).

### 2. `src/config/navConfig.ts` (Navigation Schema)

Defines the structure for top-level navigation, desktop hover dropdown menus, and mobile drawer items:

- Each item is typed via `NavItem`:
  ```typescript
  export interface NavItem {
    label: string;
    path: string; // Destination route or fallback
    subLinks?: NavSubLink[]; // Submenu items for dropdown/drawer
    remote?: boolean; // Opens in external tab if true
    superButton?: boolean; // Renders as a highlighted CTA button (e.g. Kontakt)
  }
  ```
- Sub-menus are structured hierarchically (e.g., "Sektionen", "Organ och Nämnder", "Nyantagen").
- Consumed by `Header.tsx`, `NavItemButton.tsx`, and `NavSidebar.tsx`.

### 3. `src/config/roles.yaml` (Legacy Static Roles)

- **Status:** **Legacy**
- **Background:** In earlier iterations of the website, chapter boards, committees, and elected officials were defined statically in this YAML file.
- **Current Architecture:** Chapter roles and group assignments are now managed and loaded dynamically from the backend API via `GET /groups` (`src/services/groups.ts`). The `GroupProvider` (`src/contexts/GroupContext.tsx`) provides these roles across the frontend in real time, making `roles.yaml` obsolete for production data.
